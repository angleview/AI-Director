# 原型代码审计（2026-08-06）

## 结论

当前工程是一个功能集中、便于演示的 Python 原型，但还不是可复现、可测量或并发安全的端侧 AI 系统。最有价值的升级方向不是继续增加手势，而是把“摄像头到模型到控制到推流”重构为只有一个所有者的实时流水线，并用树莓派数据证明每一项性能结论。

## P0：先修复，否则结果不可信

### 1. 每个网页客户端都会复制整套推理与控制

`/video_feed` 每次请求都会创建新的 `generate_frames()`。推理、状态机、舵机控制、变焦、绘制和 JPEG 编码都位于该生成器内，因此两个客户端意味着两套循环同时调用共享模型、修改全局状态并控制同一云台。

影响：模型后端可能遭遇并发调用，统计结果随客户端数量变化，舵机会接收竞争命令；README 所说的“高并发”不能成立。

建议：建立单一处理流水线，客户端只读取同一份最新编码帧与不可变状态快照。

### 2. 模型与依赖不可复现

本机缺少 `model.ncnn.bin`，备用 `yolov8n-pose.pt` 又被 `.gitignore` 排除；`requirements.txt` 没有版本、平台或 Python 版本约束。模型加载使用裸异常捕获，NCNN 失败后可能尝试一个同样不存在的文件。

影响：换一张 SD 卡或换一台开发机无法按 README 重建环境，也无法确认实验使用了哪个后端和权重。

建议：记录模型来源、导出命令、校验和、许可证和后端版本；启动时检查资产并给出明确错误，不静默回退。

### 3. README 的关键性能表述与实现不一致

- 摄像头 MJPEG 会被 OpenCV `retrieve()` 解码，处理后又由 `cv2.imencode()` 用 CPU 编码，不是 MJPEG 码流透传。
- 配置是 1920×1080，页面却显示 `LIVE 720P`，注释还混用 1280×720、320×240 和 480×270。
- `digital_zoom()` 是裁剪后插值回原尺寸，会损失信息，不能称为“无损数字变焦”。
- 代码没有选择 NCNN Vulkan/GPU 路径，也没有相关测量，不能仅凭使用 NCNN 宣称“异构加速”。
- 没有证据表明端到端输出达到 1080P@30fps 或“广播级低延迟”。

建议：先将 README 降级为待验证目标；性能报告形成后再恢复有数字依据的表述。

## P1：决定系统深度的工程问题

### 4. 所谓低分辨率推理可能仍以 640×640 执行

代码先把帧缩放到 480×270，但调用 `model(ai_frame)` 时没有指定 `imgsz`；模型元数据记录的输入尺寸是 640×640。Ultralytics 仍可能把输入预处理到模型默认尺寸，因此前一次缩放不等于模型真的在 480×270 上推理。

建议：记录进入 NCNN 的真实 tensor 形状，明确动态/固定输入限制，并对 320、416、480、640 等尺寸测量精度、推理耗时和端到端延迟。

### 5. 目标选择不是跟踪

当前逻辑按检测框面积排序并选择最多两个人，没有时序身份、运动预测、丢失恢复或切换滞回。多人交叉或面积接近时，主目标可能逐帧切换，造成云台抖动。

建议：把检测与目标选择分开，增加持久 Track ID、切换代价、短时丢失保持和可测的重捕获时间。

### 6. 手势和姿态阈值与分辨率绑定

手腕距离 `60`、纵坐标 `240`、死区 `15` 都是固定像素值；关键点只检查坐标是否大于零，没有使用关键点置信度。输入尺寸、人物远近或遮挡变化都会改变行为。

建议：使用人体尺度归一化阈值与关键点置信度，添加进入/退出滞回、连续帧确认和冷却时间。

### 7. `LOCKED` 模式没有手势边沿检测

左手抬起会从 `TRACKING` 进入 `LOCKED`，下一次推理若手仍举着，同一个条件又会立刻解锁。类似问题也会使重置手势连续触发。

建议：将手势识别结果转成带时间戳的事件，只在“未触发→触发”的边沿改变状态。

### 8. 重置动作没有同步软件控制状态

`generate_frames()` 中对 `real_pan, real_tilt` 的赋值没有声明为全局，因此只更新了局部变量并直接写一次舵机；下一次平滑控制仍基于旧的全局角度，可能产生跳变。

建议：执行机构状态由单一控制器拥有，所有模式只提交 `ControlIntent`，禁止跨模块直接写舵机。

### 9. 控制器不是 PID，且缺少安全约束

实现是比例控制、死区和指数平滑，没有积分项、微分项、采样周期建模或系统辨识。搜索模式按墙钟三角函数直接计算角度；异常被吞掉，也没有舵机速率、加速度、看门狗或退出安全位。

建议：准确称为 P+EMA 控制器；先测量舵机响应，再决定是否使用 PI/PID。无论算法如何，都要加入角度、速度、命令频率和失联安全约束。

### 10. 指标不是它们声称测量的对象

`GLOBAL_STATS['cpu']` 实际保存温度；`fps` 是单个 HTTP 生成器循环的瞬时倒数，不等于摄像头 FPS、推理 FPS 或端到端输出 FPS。所有统计均为无锁全局可变字典。

建议：分别定义 capture FPS、inference FPS、publish FPS、frame age、阶段耗时分位数、丢帧数、温度、CPU 和 RSS，并发布不可变快照。

## P2：可维护性与产品化

- 模块导入时立即打开摄像头、初始化舵机、加载模型并等待两秒，导致测试和工具导入都触发硬件副作用。
- 大量裸 `except` 隐藏根因，程序可能以“看似运行但没有硬件”的状态继续。
- 摄像头线程没有上下文管理或可靠退出；Flask 开发服务器也不是部署边界。
- HTML/CSS/JavaScript 嵌在 Python 字符串中，无法单独测试、缓存或演进。
- 没有配置文件、结构化日志、健康检查、单元测试、固定输入样例或故障注入。
- `model_ncnn.py` 使用 Windows 风格反斜杠路径并引入 Torch 生成随机输入，不属于主程序真实部署链路。

## 推荐目标架构

```text
CameraSource -> LatestFrameBuffer -> InferenceBackend -> TargetSelector
                                                        |
                                                        v
Web clients <- EncodedFramePublisher <- Renderer <- StateMachine
                                                        |
                                                        v
                                            MotionController -> Actuator

                         Metrics collects timestamps and counters from every stage
```

关键约束：采集、模型、状态机和执行器各有唯一所有者；阶段之间传递带序号和时间戳的不可变消息；缓冲区有界且显式采用“旧帧可丢、控制命令不可乱序”的策略。

## 面向岗位的深化实验

1. **部署主线**：完成 `.pt -> ONNX -> NCNN` 可重复导出，记录算子、精度格式、模型大小、加载时间与校验和。
2. **性能主线**：分解采集、颜色转换/缩放、推理、后处理、控制和编码耗时，报告 P50/P95/P99 与 frame age。
3. **边缘系统主线**：实现有界队列、背压、故障恢复、systemd 服务、健康检查和 30–60 分钟热稳定测试。
4. **智能硬件主线**：标定舵机机械零位、软件角度和画面误差的关系，评估超调、稳态误差与目标重捕获时间。
5. **嵌入式/DSP 支线**：对 resize + BGR/RGB + normalize 实现 C++ 标量和 ARM NEON 两版，比较吞吐、内存带宽与误差，再与 OpenCV 基线对照。

## 建议实施顺序

1. 恢复摄像头可见性，保存不可变测试视频和原型真实性能基线。
2. 建立配置、模拟硬件、类型和测试边界，消除导入副作用与裸异常。
3. 实现单流水线与共享输出，再复测多客户端情况下的资源占用。
4. 完成模型导出/输入尺寸/线程数/量化对照，选择有数据支持的配置。
5. 最后做 C++/NEON 实验、长期稳定性测试和求职材料。
