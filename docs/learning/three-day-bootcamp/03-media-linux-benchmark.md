# 第二天下半场与第三天基础：视频、并发、Linux 接口与测量

第二天用约 4 小时学第 1–6 节，另用 2 小时复述、做题；第三天用约 2 小时复习第 7–9 节。目标是面对“为什么、怎么测、哪里有问题、怎样改进”时能给出具体解释。

## 1. 先分清像素、编码和协议

| 概念 | 含义 | 在项目中 |
| --- | --- | --- |
| 像素图像 | 解码后的二维/三维数据 | OpenCV 图像数组 |
| JPEG | 一张图像的压缩编码 | 原型 imencode 输出 |
| MJPEG | 多张独立 JPEG 组成运动画面 | 摄像头请求格式、HTTP 画面输出 |
| H.265/HEVC | 利用空间与时间冗余的视频编码标准 | 未发现使用它转码的实现 |
| AVI | 文件容器，不是唯一编码 | 静态回放使用 MJPEG AVI |
| HTTP multipart | 一个 HTTP 响应中分段传内容 | Flask 视频接口 |

MJPEG 各帧独立，易于逐帧处理和输出；H.265 涉及帧间预测和参考关系，编解码链路不同。设备有 HEVC 解码节点，不能证明 Python 程序打开或使用了它。

### 本项目是否 H.265 转 MJPEG

**没有相关代码证据。**原型通过 OpenCV 请求摄像头 MJPG，解码为图像，处理后再编码 JPEG，通过 HTTP multipart 输出。要声称 H.265 转 MJPEG，应能给出输入 HEVC 码流、解码组件、输出 JPEG 编码和运行记录；当前都没有该链路证据。

## 2. 原型的视频链路，按函数追踪

从 `main.py` 搜索 `VideoCapture`、`update`、`read`、`generate_frames`、`imencode`、`video_feed`。

~~~text
摄像头格式/分辨率/FPS 请求
 → 后台线程 grab/retrieve
 → 翻转图像，锁内更新共享 frame
 → 输出生成器 read 并复制
 → 缩小 AI 图像，每 3 次生成器迭代尝试推理
 → 模式、云台意图、裁剪/缩放/叠加
 → JPEG 编码
 → HTTP multipart 分段
 → 浏览器 img
~~~

请求 MJPG、1920×1080、30 fps、buffersize=1 只是设置意图，未验证驱动实际协商结果。OpenCV 底层可能使用 Linux 视频后端，但原型没有直接实现 V4L2 ioctl/mmap；应说“通过 OpenCV 采集”，而不是“自行实现 V4L2 驱动”。

`grab` 获取下一帧，`retrieve` 取出/解码已抓取帧；具体行为依赖后端。API 可参考 [OpenCV VideoCapture](https://docs.opencv.org/4.x/d8/dfe/classcv_1_1VideoCapture.html)。采用这两个调用不自动证明硬件解码、DMA 或零拷贝。

### 为什么需要解码和重新编码

推理、裁剪和叠加需要访问像素；JPEG 字节不能直接当图像矩阵处理。输出又需要适合传输的压缩帧，因此 `cv2.imencode('.jpg', ...)` 重编码。JPEG 有损，裁剪再插值放大不能创造原图没有的细节，因此不叫无损变焦。

### 推理间隔的实际含义

`AI_INTERVAL=3` 计数的是每个输出生成器的循环，不是摄像头采集序列。采集与消费速度不同，可能跳过帧或再次使用同一最新图像；不能直接用“摄像头 30 fps / 3”证明推理 10 fps。

## 3. Flask、生成器和多客户端问题

Flask 把 URL 交给处理函数。`/video_feed` 返回 Response，内部传入 `generate_frames()`，逐段输出字节。

简化的分段结构：

~~~text
--frame
Content-Type: image/jpeg

一张 JPEG 的二进制数据
--frame
Content-Type: image/jpeg

下一张 JPEG
~~~

实际行分隔使用 CRLF，边界名字应与响应参数一致。它是一条持续 HTTP 响应，不是每帧新开一个 HTTP 请求。Flask 支持生成器流式响应，见 [官方 Streaming Contents](https://flask.palletsprojects.com/en/stable/patterns/streaming/)。

**原型关键缺陷：**每个浏览器请求创建一个独立生成器；而生成器同时执行推理、状态变化、控制和编码。两个客户端就可能有两套调用争用同一个全局模型、状态和云台。摄像头锁只保护 frame 读写，没有保护这些业务状态。

### 正确的改进设计怎样讲

~~~text
一个采集端 → 有界最新帧缓冲 → 一个推理/决策/控制端 → 一个编码输出
                                                       ↓
                                   多个客户端读取相同已发布 JPEG
~~~

单一控制所有者避免多客户端重复驱动。客户端变成消费者；慢客户端不应让核心无限堆帧。需要断开处理、发布版本号、线程同步和资源关闭机制。

这是项目 ADR 的架构方向。当前新代码实现了同步参考核心，尚未实现这张图中的完整并发和共享网页发布；面试回答要用“计划/设计”，不要说“已经部署完成”。

## 4. 吞吐、延迟和背压

吞吐是单位时间完成多少帧；延迟是一帧从某个明确入口到出口花多久。它们不是同一个指标。

假设输入 30 fps，处理能力 10 fps：

- 无限队列每秒积压约 20 帧，画面越来越旧。
- 阻塞生产端可能把积压推回采集/驱动端，仍需检查缓冲行为。
- 容量 1 的最新帧策略舍弃过期图像，适合很多视觉控制任务，但不适合必须逐帧保存的视频归档。

每帧 100 ms 的串行处理约为 10 帧/秒的能力估算；并行流水线的吞吐由瓶颈阶段决定，同时还受队列、资源竞争等影响。不能单看某一阶段的倒数宣称整机帧率。

时间戳建议：输入获取时间、推理完成、控制发出、编码/发送完成。计算时用同一单调时钟。当前离线视频源在解码后标记 captured_at_ns，所以其 frame_age 不是从真实传感器曝光开始的延迟。

## 5. 读懂性能脚本

阅读 `benchmark.py` 的 run_benchmark、percentile、summarize：

1. 检查输入与模型必要文件。
2. 记录环境和资产哈希。
3. 加载模型对象并记录 setup.model_load_ms。
4. 预热 5 次，不计入稳态轮次。
5. 测 30 次，每轮重新读取固定图片并预测。
6. 保存解码、框架预处理/推理/后处理、predict 调用墙钟、固定图片端到端。
7. 保存全部轮次、分位数、温度与节流标志。

模型构造后可能仍在第一次 predict 进行惰性初始化，因此 model_load_ms 不能无条件叫“完整冷启动”。若测冷启动，应在独立进程测启动至首个有效结果，另保留稳态统计。

### 分位数手算

排序样本 `[10, 20, 30, 40, 100]`，本项目采用线性插值：

~~~text
位置 = (n−1) × q
P50：位置 2 → 30
P95：位置 3.8 → 40 + 0.8 × (100−40) = 88
~~~

P95 描述经验延迟分布的尾部；样本只有 30 轮，不能证明极端长尾和长期稳定。不要说“每帧都低于 P95”。

各阶段 P50 相加不严格等于端到端 P50，因为不同阶段中位数可能来自不同轮次，还有包装器开销。对比原始每轮值比强行相加摘要更可靠。

## 6. 两个必须会讲的实测结果

条件：Pi 5、Cortex-A76、历史 Python 3.13.5 / Ultralytics 8.3.232 / NCNN 1.0.20250916，固定 bus.jpg，同一导出模型，5 次预热＋30 次测量，conf 0.25。

| 指标，单位 ms | 640 P50/P95 | 480 P50/P95 |
| --- | --- | --- |
| 模型推理 | 76.60 / 77.22 | 42.17 / 170.34 |
| 后处理 | 1.57 / 2.11 | 1113.33 / 1256.59 |
| 固定图片端到端 | 91.49 / 92.97 | 1229.42 / 1400.26 |
| 检测数量 | 每轮 4 | 每轮 300 |

依据：实验报告及 `artifacts/benchmarks/` 两份 JSON。端到端这里是**文件解码到 Results**，不包括摄像头、控制、网页编码、网络和浏览器显示。

### 480 对照如何解释

观察：推理 P50 降约 44.9%，但后处理激增，总耗时约 13.44 倍。网络推理 P95 本身也变差。640 固定导出物直接用 480 调用，是一次被拒绝的运行配置；不能宣布“分辨率优化成功”。

推测：固定导出形状与运行配置的兼容/输出解码可能异常。当前证据没有完全隔离根因，不能断言某一个算子有 bug。

验证方案：同一权重原生导出 480；保留原生 640 对照；先检查输入输出形状、候选框与关键点正确性，再测相同数据、依赖、线程、温度和轮次。正确性不过关的性能对比没有业务意义。

### 静态回放是什么证据

同一图片组成 3 秒、10 fps、30 帧的 MJPEG AVI，经真实 NCNN、状态机、控制器和虚拟执行器：

- 序号 0–29，共 30 帧，每帧选择 2 人。
- 22 帧 TRACKING，8 帧 SHOWCASE。
- 核心阶段 total P50/P95 92.85/99.12 ms。

这证明计算链可串联及记录，不证明运动场景跟踪、真实手势抗抖、摄像头实时性或机械控制精度。视频时长、处理运行时间和每帧流水线统计口径不同。

电脑上运行 `practice.py evidence`，它读取保存产物、复算统计，没有启动推理。遇到报告变化会报差异，先查证据，不能为了通过检查改数字。

## 7. Linux 进程、线程、锁和 GIL

进程通常具有独立虚拟地址空间；线程共享所属进程的内存。线程适合等待摄像头或网络，但共享数据需要同步。上下文切换、缓存竞争和内存复制都有代价，线程越多不一定越快。

### 共享图像的风险

生产者写图像，消费者同时读图像，可能看到更新中间状态。原型在锁内替换 frame，读者在锁内复制成自己的快照。锁保证受保护区域互斥，但复制有开销；更完善的缓冲设计仍需明确所有权和生命周期。

### GIL 不能替代业务锁

普通启用 GIL 的 CPython 同时通常只有一个线程执行 Python 字节码，许多本地扩展可在计算或等待时释放 GIL。多步业务更新仍可能交错，模型本地代码也可能并行；GIL 不能保证整个“读取状态→决策→控制”事务正确。

Python 3.13 起存在可禁用 GIL 的 free-threaded 构建，不能把它当所有部署的默认情况。参考 [Python 3.13 threading](https://docs.python.org/3.13/library/threading.html)。项目没有记录自己使用无 GIL 构建，也没有多线程加速实验。

守护线程可能随进程退出而突然停止；工程上应设计停止标志、join、设备 release 和错误传播。新核心的 with 用于释放视频源，但完整实时服务的生命周期机制仍待实现。

## 8. I²C、PWM、PCA9685 与 ARM

I²C 是串行控制总线，常用 SDA/SCL，两端通过地址选择器件；不是用来传整路高清图像的接口。PWM 是脉冲宽度调制，是信号形式而非同类通信协议。

原型 `ServoKit(channels=16)`，pan 通道 1、tilt 通道 0；通过 servo[channel].angle 发送期望角度，驱动库通常借助 PCA9685 生成多路 PWM。没有直接实现 I²C 寄存器驱动。

PCA9685 具有 16 路、12 位 PWM；其机制见 [NXP 数据手册](https://www.nxp.com/docs/en/data-sheet/PCA9685.pdf)。以常见示例 50 Hz 为例：

~~~text
周期 T = 1/50 s = 20 ms
计数分辨率 = 20 ms / 4096 ≈ 4.88 μs
1.5 ms 脉宽约对应 307 个计数
~~~

50 Hz 和脉宽范围必须按实际舵机规格确认；示例不是本项目实测配置。舵机主要依据脉宽控制位置，不能只把占空比增大解释为任意电机转速增大。

ARM 是处理器架构。Pi 的 Cortex-A76 跑 Linux；Cortex-M 常用于 MCU，运行裸机或 RTOS。AArch64 是 64 位 ARM 执行环境。NEON 是 SIMD 能力，一条指令处理多个数据元素；硬件能力和库可能使用它，不构成自己编写或优化 NEON 的证据。

**实时性**要求定义时限并验证最坏或尾部行为。Linux 可以有实时相关配置，但当前项目没有实时内核调优、调度策略或最坏执行时间保证，不能因控制舵机就叫硬实时系统。

## 10. 验收：用一分钟讲出失败实验

推荐结构：“我本来想用较小输入降低推理成本；在同一固定导出物上对照发现，480 虽然推理中位数更低，但最终输出检测框数量从 4 变到 300，后处理超过一秒，整体明显更慢。因此保留 640，不把这次配置当优化。下一步原生导出 480 并先验证输出正确性，再比较端到端。”

自测：H.265 是否存在？为什么两个浏览器可能重复控制？P95 是什么？frame_age 起点在哪？虚拟回放证明什么？这些问题都应答到具体代码或产物。
