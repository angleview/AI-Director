## 2. 笔试前先认识复杂度

时间复杂度描述输入规模增长时步骤数量如何增长，不直接是毫秒。

| 操作/算法 | 常见复杂度 | 项目关联 |
| --- | --- | --- |
| 遍历 n 个目标 | O(n) | 过滤、平均位置 |
| 字典查询 | 平均 O(1)，极端碰撞可退化 | 通过帧号找观测 |
| 排序 n 个候选 | O(n log n) | 按面积选择目标 |
| 双重遍历全部对 | O(n²) | 朴素两数之和、简单两两筛选 |
| 二分有序序列 | O(log n) | 基础笔试能力 |

空间复杂度关注额外存储。排序是否原地、是否先复制，会影响空间；不要只背一种语言所有函数的固定复杂度。只有两个已选目标的平均很小，但框数量在后处理前可能很大。

## 3. 两道必做编程题

每题先用纸写思路和边界，再写代码，最后看 practice.py 的函数。运行现成答案不等于自己完成。

### 题 A：从手势序列提取事件（约 25 分钟）

输入：`["NONE", "LEFT", "LEFT", "NONE", "LEFT", "BOTH"]`。

输出：`[(1, "LEFT"), (4, "LEFT"), (5, "BOTH")]`。

规则：非 NONE 且不同于上一帧才有事件。空输入返回空列表，持续 LEFT 只触发一次；LEFT→BOTH 会触发。

先写函数签名：

~~~python
def gesture_edges(values: list[str]) -> list[tuple[int, str]]:
    ...
~~~

思路：保存 previous，按 index 遍历；满足条件 append；每帧都更新 previous，包括 NONE。平均和最坏遍历都是 O(n)，输出额外空间 O(k)。

最常见错误：只在触发时更新 previous，导致手势释放后不能再次触发；或者把 LEFT→BOTH 当作必须先 NONE 才能触发，与项目不同。

### 题 B：两数之和（约 30 分钟）

给定整数列表和 target，返回两个不同元素的下标；无解返回 None。`[2,7,11,15], 9 → (0,1)`。`[3,3], 6 → (0,1)`。

思路：遍历 value，先在字典里查 target−value；找到就返回；未找到才存当前值及下标。这样不会重复使用当前元素。平均 O(n) 时间、O(n) 额外空间；哈希最坏情况另论。

检查：空列表、一个元素、重复值、负数、无解。参考答案在 practice.py 的 two_sum。

### 加练 C：分位数（约 25 分钟，选做）

不调用 NumPy，按 `(n−1)×q` 线性插值返回分位数。样本 `[100,10,40,20,30]` 的 P50=30，P95=88；空样本和 q 不在 [0,1] 时抛 ValueError。

先排序，再找相邻位置，复杂度 O(n log n)，排序副本 O(n) 空间。参考 sample_percentile；单元素时 lower=upper，仍应正确。

### 加练 D：二分查找（选做）

输入升序数组和目标，返回下标或 −1：

~~~python
def binary_search(values, target):
    left, right = 0, len(values) - 1
    while left <= right:
        middle = (left + right) // 2
        if values[middle] == target:
            return middle
        if values[middle] < target:
            left = middle + 1
        else:
            right = middle - 1
    return -1
~~~

验证 `([],2)`、`([2],2)`、`([1,3,5],4)` 和首尾元素。O(log n) 时间、O(1) 额外空间；有重复值时返回某个匹配，不保证第一个。

运行附带检查：

~~~powershell
python docs/learning/three-day-bootcamp/practice.py exercises
~~~

## 4. C/C++ 入门补充：先能读，再谈熟练

项目应用核心主要是 Python，没有自己实现 C/C++ 推理引擎或 NEON 算子的证据。以下是嵌入式笔试补充，不是本项目已完成的技术点。

### 4.1 编译、类型与指针

C/C++ 源文件需要经过编译、链接成为目标平台程序；x86 程序不能默认在 ARM 上运行。交叉编译是在一种平台构建另一种平台的程序，本项目尚无自主工具链交叉编译记录。

~~~c
int angle = 10;
int *p = &angle;
*p = 20;             /* 修改 p 指向的 angle */
~~~

`&angle` 取地址，`p` 保存地址，`*p` 访问该地址的对象。局部数组不会自动做越界检查；返回局部变量地址会产生悬垂指针。

数组在很多表达式中会转换为指针，但数组与指针不是同一种对象。`sizeof(array)` 在数组定义所在作用域可得到整个数组字节数；函数参数写为数组形式时往往已经调整为指针，不能用它推算元素个数。

### 4.2 内存与生命周期

局部自动对象通常随作用域结束销毁；动态申请的资源需按所有权释放。常见问题：泄漏、重复释放、悬垂指针、越界访问。

C++ 可用 RAII 把资源生命周期绑定到对象；类似思路在 Python 中体现为 with 确保资源关闭，但语言机制不完全相同。不要将“Python 自动管理引用”理解为设备和文件永远不用显式关闭。

### 4.3 const、static、volatile

- const 限制通过某个声明的修改行为；不是线程同步机制。
- static 的含义依作用域而定，例如局部静态对象跨调用保留、文件作用域内部链接。
- volatile 涉及编译器对对象访问的处理，常见于硬件寄存器语境；不提供跨线程原子性或完整内存同步。
- 共享状态应使用适合平台的锁或原子操作，不靠 volatile 或 GIL 猜测。

今天只要求解释以上概念并读懂小例子。C/C++ 岗位常需要进一步手写代码、调试和内存问题专项练习。

## 5. RTOS 补充：当前项目没有 RTOS

Pi 上运行 Debian/Linux、Python 线程和 Flask；没有 FreeRTOS、RT-Thread、Zephyr 等任务调度实现。Python 状态机也不是 RTOS 调度器。

RTOS 的学习价值是理解有时限的任务如何调度。常见单核抢占式思路：最高优先级的就绪任务获得运行机会；任务等待队列/延时进入阻塞，事件到来后回到就绪。具体规则由系统和配置决定。

| 概念 | 解释 | 面试要点 |
| --- | --- | --- |
| Running/Ready/Blocked/Suspended | 正在运行、可运行、等待、挂起 | 阻塞等待通常不占着 CPU 忙等 |
| 任务优先级 | 影响就绪任务选择 | 不是“所有任务平分时间” |
| Queue | 任务间传数据/消息 | 谁发送、谁消费、容量与超时 |
| Semaphore | 通知或计数同步 | 不能一概当有所有权的锁 |
| Mutex | 保护共享资源，通常有所有者 | 可有优先级继承机制 |
| ISR | 中断处理例程 | 尽量短，用适合中断的非阻塞 API |
| Tick | 内核时间基准之一 | 与业务采样周期、最坏响应时间不同 |

优先级反转例子：低优先级任务 L 持锁，高优先级 H 等锁，中优先级 M 抢占 L，导致 H 间接受 M 延误。优先级继承让持锁 L 暂时提升，有助于释放锁；不是消灭所有调度延迟。

如果未来设计“Pi 视觉＋MCU 控制”：Pi 发送有序号、时间戳和校验的目标命令；MCU 周期控制，检查过期与失联，限制动作。这里是迁移方案，仓库没有这套通信与 RTOS 代码。

资料入口：[FreeRTOS 官方内核仓库及其文档链接](https://github.com/FreeRTOS/FreeRTOS-Kernel)。三天内不用迁移整个项目来补一条 RTOS 经历；应在后续用实际 MCU 或官方仿真例程做独立实验。

## 6. 网络基础：能解释网页为何能看到 Pi

IP 定位主机；端口帮助定位服务；HTTP 定义请求响应。原型监听地址和端口决定可访问范围，浏览器访问的主机地址不等于总写 localhost。

TCP 提供有序可靠的字节流，可能重传且没有应用消息边界；UDP 提供数据报，不自动保证送达或顺序。可靠传输也会出现延迟和缓冲积压。这个项目的 MJPEG 页面通过 HTTP/TCP，不是已经实现 RTSP/RTP。

网络通却网页打不开，依次查：进程是否运行 → 端口是否监听 → 监听地址 → 网络路径/防火墙 → HTTP 响应 → 摄像头/模型服务内部异常。TCP 机制可查 [Linux tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html)。

## 8. 项目介绍：三种长度

以下为项目事实讲解稿。你需要单独补上真实角色、时间和个人工作；不能把本次整理或已有代码自动说成自己全部开发。

### 30 秒：问题与链路

> 这是一个基于树莓派的端侧视觉构图项目，目标是根据人的位置和姿态生成画面调整与云台控制意图。它通过 YOLOv8n Pose 和 NCNN 获取人体框及关键点，再由状态机和比例控制逻辑决定行为。项目保留了摄像头到网页的原型，也建立了可回放、可测试的核心；目前真实验证到 Pi 推理和虚拟控制，机械闭环还有待验证。

### 90 秒：加入工程问题与证据

> 项目希望在树莓派本地完成视觉感知和构图决策。原型用 OpenCV 采集，调用 YOLOv8n Pose 的 NCNN 后端，再根据人体位置和几何手势控制模式、产生云台动作，并通过 Flask 输出 MJPEG 画面。
>
> 工程上有两个值得展开的问题。一个是原型每个视频客户端都触发自己的处理生成器，会重复推理并竞争全局状态与云台；因此实验部分先建立同步核心，把帧、观测、状态决策和控制意图明确分开，并通过虚拟执行器验证顺序与限位。另一个是性能不能只看网络计算。在 Pi 5 固定图片实验里，640 的推理 P50 约 76.6 ms，文件解码到结果约 91.5 ms；直接改用 480 后虽然推理中位数降低，但最终输出检测框数量和后处理耗时异常增大，总体反而更慢。
>
> 当前保存了 11 项核心测试和 30 帧真实 NCNN 静态回放证据。这个结果证明计算链路，不等于完成动态身份跟踪、实机控制精度或 1080p 30 FPS。个人负责的部分是【填写真实模块与实际工作】，下一步计划是【选择一项真实计划】。

### 5 分钟：不用背长文，按六个段落讲

1. 约 30 秒：使用场景、输入输出、真实个人职责。
2. 约 60 秒：架构及旧原型与新核心关系。
3. 约 60 秒：深入一个问题，例如客户端竞争，给出调用证据和设计方向。
4. 约 60 秒：解释基准方法、640/480 结果、为什么拒绝坏配置。
5. 约 30 秒：测试和回放的价值及边界。
6. 约 60 秒：待解决风险、下一次实验如何验收。

录音后核对实际时长。删掉无证据形容词，保留输入、机制、结果和判断。听完应能让对方选择一个技术点继续问。

## 9. 深度追问怎么组织答案

采用四步：

1. 先直接回答结论。
2. 给机制或一个手算例子。
3. 指到项目函数、配置或实验字段。
4. 说清限制，以及怎样验证尚未解决的问题。

例如“是 PID 吗”：

> 当前是比例控制，配合死区和限幅；旧原型还有指数平滑。control.py 只根据当前位置误差乘增益，没有误差积分、变化率和 dt，因此不能叫完整 PID。若后续加入机械闭环，先测采样周期与响应，再决定控制器并验证过冲和稳态误差。

追到不会的地方：

> 目前能确认的是【观察与证据】；【具体根因】还没有通过对照隔离。我会固定其他条件，改变【变量】，检查【正确性与性能指标】来验证。

这样才能区分工程判断与臆测；不要把缺口藏在一串术语里。
