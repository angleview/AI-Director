# 第二课：第一次真实 NCNN 推理与可信基准

这一课的目标不是得到一个好看的 FPS，而是回答一个更重要的问题：同一个模型、同一个输入、同一台树莓派，别人能否复现你的结果，并知道每个数字到底测了什么。

## 从“流程能跑”到“模型真跑”

第一课使用 `ScriptedInferenceBackend` 验证状态机和控制链路，它的价值是确定软件语义，但它没有执行神经网络。第二课直接加载 Ultralytics 导出的 NCNN 模型目录，调用真实姿态推理。两者不能混为一谈：前者证明架构可测，后者才产生端侧计算性能证据。

固定输入图片不代表项目只能处理图片。固定输入控制了内容变量，使不同版本的耗时有可比性。以后接入视频回放时，再测连续输入、吞吐率和帧龄。

## 测量边界

基准脚本为每轮保留原始记录，并给出均值、P50、P95 和 P99：

- `decode_ms`：OpenCV 从文件读取并解码图片。
- `preprocess_ms`：Ultralytics 报告的缩放、填充、排布等预处理耗时。
- `inference_ms`：Ultralytics/NCNN 报告的模型执行耗时。
- `postprocess_ms`：输出解码、筛选等后处理耗时。
- `predict_wall_ms`：从调用框架到拿到 `Results` 的外部墙钟时间。
- `end_to_end_ms`：本实验边界内，从开始读取文件到拿到 `Results` 的墙钟时间。

模型加载时间单列，不混进逐帧延迟。预热轮次会触发首次初始化和缓存，但不进入统计。`framework_overhead_ms` 是墙钟时间减去框架上报阶段之和，它可帮助发现 Python 调度或框架包装开销；出现轻微负值时应理解为计时边界和精度不同，而不是“负开销”。

## 为什么不能只报平均 FPS

平均值会掩盖尾延迟。交互式智能硬件常常更关心 P95：一百次里较慢的那几次是否让画面或控制明显卡顿。FPS 也容易混淆吞吐率和单帧延迟；同步单流中可以用 `1000 / P50端到端毫秒` 估算理想速率，但不能把它当成并发流水线的实测吞吐率。

脚本同时记录输入、模型文件的 SHA-256，系统架构、Python 和关键依赖版本，以及树莓派温度和节流标志。没有这些元数据，优化前后的数字很可能不可比。

## 在树莓派上运行

```bash
cd .
PYTHONPATH=src python3 -m edge_ai_director.benchmark \
  --model yolov8n-pose_ncnn_model \
  --source assets/inputs/bus.jpg \
  --output results/benchmark-640.json \
  --warmup 5 --runs 30 --imgsz 640
```

运行后先检查 JSON 中的 `configuration`、哈希、环境和每一轮 `measurements`，再引用 `summary_ms`。如果输入、频率策略、温度、线程数或模型文件变化，应生成新的结果文件，而不是覆盖旧结论。

## 你应该能回答的面试问题

1. 为什么模型加载时间不计入逐帧延迟？冷启动场景又该怎么测？
2. 为什么预热要排除？排除预热是否等于隐藏真实性能？
3. 框架上报的 `inference_ms` 为什么可能明显小于端到端延迟？
4. P50、P95 和吞吐率分别描述什么，实时系统应该优先看哪个？
5. 固定输入能证明什么，不能证明模型精度或业务鲁棒性的哪些部分？
6. 如何设计一次输入尺寸、线程数或量化格式的对照实验，保证只有一个变量发生变化？

完成标准：树莓派能生成包含原始轮次、环境、校验和及分阶段统计的 JSON；README 中引用的任何性能数字都能追溯到该文件。
